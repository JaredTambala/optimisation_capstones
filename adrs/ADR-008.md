# ADR-008 — Scenario dataset packages

| Field | Value |
|---|---|
| Status | ACCEPTED |
| Owner | Domain lead |
| Reviewers | Data lead, Evaluation lead |
| Approval date | 19 August 2026 |

## Context

CAP-001 supplies BASE and five controlled disruptions. Each scenario represents
a complete business-data reality. The candidate should demonstrate that its
application can replace the whole dataset, validate it, reconstruct a generic
MILP or MINLP and apply separately declared policies and overrides. Requiring
the application to combine a central BASE directory with a selected delta would
test a narrower, scenario-specific integration pattern.

Some required facts are period-grained, while `shipping_lanes.csv` and several
other dimension tables are not. A self-contained scenario package therefore
still needs its own `disruption_impacts.csv`. Using the same package-local
contract for capacity, logistics, cost and demand changes also prevents mixed
or double-applied semantics. Those rows are part of the selected dataset, not a
reference to data held elsewhere.

Historical performance and incidents remain exploratory. They can support a
candidate's resilience rules and recommendation, but must not silently change
mathematical inputs. The assessed default case must remain reproducible even
when an application supports sensitivity controls.

## Decision

Accepted on 19 August 2026.

1. The release contains six self-contained dataset packages: BASE and SCN-01
   through SCN-05. Each package contains all 26 raw CSVs, a manifest, individual
   file checksums and an aggregate dataset hash.
2. A run reads exactly one dataset root. Missing files may not be inherited from
   BASE, another scenario or a shared parent directory. Symlinks and implicit
   fallbacks are prohibited in the released packages.
3. `disruption_scenarios.csv` contains the selected package's one scenario
   record. `disruption_impacts.csv` contains only that package's applicable
   period-specific impact and recovery rows and is header-only for BASE.
4. Every raw file in the selected package is authoritative. Candidate code
   derives dimensions and parameters afresh and must not retain stale state from
   the previously loaded package.
5. The first controlled stress set expresses its scenario changes through
   package-local impact rows. Those rows are not also pre-applied to another raw
   fact table. One generic resolver supports
   node, organisation, parent group, region, lane, recipe, material, external-
   price, conversion-cost and terminal-demand targets. Scenario identifiers do
   not select bespoke equations.
6. `availability_flag=false` takes precedence over capacity or lane
   multipliers. Applicable multiplicative impacts compose by multiplication.
   Replacement is allowed only for a declared field; the highest priority wins
   and a tie at the winning priority is invalid.
7. Transit impacts apply before weekly ceiling and arrival indexing. Recovery
   is expressed through explicit later-period rows and is not inferred from a
   scenario name, a missing row or another package.
8. SCN-01 through SCN-05 are retained because they test distinct external facts
   and generic system behaviours: upstream source substitution, logistics mode
   choice, Tier-1 site eligibility, correlated regional resilience and composed
   impacts with demand priority.
9. `STRESS_ONLY` evaluates a compatible stored BASE plan against the complete
   replacement dataset. `REOPTIMISE` creates a fresh model from that dataset.
   The standard evidence requires both only for the headline regional case.
10. Candidate-owned resilience rules, within-stage objective parameters and
    authorised overrides live in a separate machine-readable run-policy
    configuration. They never edit the released dataset. Every result records
    both dataset and configuration hashes.
11. An approval or eligibility exception names the affected record, original
    rule, effective rule, reason and authority. Silent use of an inactive,
    ineffective or unapproved path is a hard failure.
12. Every scenario explanation covers both the changed business data and the
    system interaction: package identity, validation, configuration, gates,
    constraints, overrides, objective effects and decision change.

## Alternatives considered

- **One BASE directory plus selectable impact overlays.** Rejected because the
  candidate would not demonstrate complete dataset replacement and a scenario
  would depend on files outside its own input root.
- **Fully bake every impact into the existing fact tables.** Rejected without a
  schema change because period-specific lane transit, capacity and freight
  cannot be represented in the current non-periodic lane table.
- **Deduplicate unchanged files through symlinks or runtime fallback.** Rejected
  because a package would cease to be portable, independently hashable and
  complete.
- **Hard-code one model branch per package.** Rejected because it does not
  demonstrate a data-driven optimisation system.
- **Require both run modes and a full narrative for every package.** Rejected as
  repetitive burden. Generic support is valuable; duplicated prose is not.
- **Convert historical performance directly into fixed objective penalties.**
  Rejected because the histories are synthetic exploratory evidence. A
  candidate may derive and justify a configured resilience rule instead.
- **Permit free-form in-place overrides.** Rejected because results would be
  irreproducible and could bypass physical, approval or accounting controls.

## Mathematical and accounting consequences

Dataset replacement changes the complete parameter and eligibility input to the
same generic physical MILP or recursive-cost MINLP; it does not introduce a new
formulation per scenario. Capacity, lane, transit, cost and demand changes must
be reflected in bounds and feasibility checks. Upstream price or conversion
changes enter at their controlled ledger stage and propagate recursively; no
package may inject an exogenous intermediate price.

The default lexicographic objective hierarchy is fixed. Declared sensitivity or
resilience configurations may add constraints, modify permitted within-stage
weights or introduce documented soft penalties, but must be reported as a
different configuration and preserve the common accounting policy.

## Data consequences

WP6 generates BASE planning facts and assembles six complete 26-file packages
from the frozen network and commercial candidates. A new dataset manifest
records package identity, compatibility and checksums. The same independent
loader and validator must accept each package without accessing another root.

Scenario packages may change any valid raw input. The first controlled set keeps
stable identifiers and complete normal facts for direct comparison, then uses
only its package-local impact rows to express the controlled shock.
`SCENARIO_CATALOGUE.md` describes all supplied packages; each package itself
contains only its own scenario metadata and impacts.

The proposal does not yet change the 26 raw schemas. A later change to manifest
fields, scenario identifiers, target vocabulary or precedence rules must update
the decision configuration and regenerate affected contracts.

## Assessment consequences

Deterministic evaluation points the candidate's declared data command at each
package in turn. It checks complete-package validation, state reset, identical
loader/model entry points, dataset and configuration hashes, approval
enforcement, package-local impact semantics and output separation.

Students provide concise comparison evidence for all packages and deeper
analysis for selected material cases. They define at least one quantitative
resilience intervention and show its cost, service, inventory and concentration
consequences under a declared configuration.

## Implementation evidence

The design was implemented and accepted on 19 August 2026. Six
complete packages, 156 schema-valid raw CSV instances, deterministic manifests,
one package-local preparation path and the independent 23-gate assessment now
exist under `capstones/CAP-001/generated/datasets/`. The bounded BASE physical
MILP check reaches zero shortage and retains no allocation. See
`docs/PLANNING_AND_DATASET_PACKAGE_IMPLEMENTATION_REPORT.md`.

The capstone owner's review accepted the generated profile and froze the
planning seed, scorecard thresholds and six package hashes recorded in the
implementation report. Any later data change is controlled regeneration and
requires renewed validation and acceptance.
